# 병합 정렬과 퀵 정렬의 성능 비교

## 1. 개요
- 무작위 정수(중복 허용)를 오름차순으로 정렬하고, **병합 정렬**과 **퀵 정렬 3종(First / Random / Median-of-Three)** 의 비교 횟수, 실행시간, 메모리 사용량을 측정했다.
- 데이터 크기: n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 같은 크기에서는 네 알고리즘이 동일한 원본의 복사본을 사용했고, 모든 결과가 올바르게 정렬되었는지 확인했다.
- 퀵 정렬은 이전 과제와 같은 구현(피벗 선택만 다르고 분할은 동일, 재귀 방식)이다.

### 측정 기준
| 항목 | 기준 |
|---|---|
| 비교 횟수 | 데이터 값끼리의 비교만 센다. 병합 정렬은 병합 중 `a[i] <= a[j]`, 퀵 정렬은 분할 중 `원소 vs 피벗`과 Median-of-Three의 중앙값 결정 비교. 반복문 인덱스·종료 조건 검사, 난수 생성, 데이터 이동은 제외 |
| 실행시간 | 정렬 호출 직전\~직후만 측정(복사·검증·출력 제외). 네 알고리즘 모두 같은 타이머, ms 단위. 네 알고리즘 모두 같은 정렬을 100회 반복한 평균을 사용(시간이 매우 짧아 타이머 정밀도와 순간적인 잡음의 영향을 줄이기 위함, 매 반복의 배열 복사는 타이머 밖) |
| 메모리 | 아래 6절 참고 (프로파일러 없이 **계산**한 값) |

> 비교 횟수와 메모리는 알고리즘의 동작으로 정해지는 값이라 같은 데이터에서는 반복해도 같으므로(Random 피벗 제외) 1회 수행한 값을 사용했다.
반면 실행시간은 정렬 한 번이 매우 짧아 타이머 정밀도와 시스템 잡음의 영향이 크므로, 이를 줄이기 위해 같은 원본 데이터를 100회 반복한 평균을 사용했다.

## 3. 데이터 크기 증가에 따른 비교 횟수 변화
- n이 2배가 될 때 비교 횟수는 병합 정렬이 약 2.17\~2.23배, 퀵 정렬(First)이 약 2.07\~2.24배로 늘었다. 2배보다 조금 큰 이 증가율은 두 알고리즘 모두 비교 횟수가 n에 선형이 아니라 **n·log n에 가깝게** 늘어난다는 뜻이다.
- n·log₂n으로 나눈 값은 병합 정렬이 0.876\~0.913, 퀵 정렬 세 방법이 1.147\~1.331 범위였다. 크기가 달라도 이 값이 거의 일정해서, 두 알고리즘 모두 n·log n 추세를 따랐다.
- **모든 크기에서 병합 정렬의 비교 횟수가 퀵 정렬 세 방법보다 적었다.** 퀵 정렬(First)은 병합 정렬의 약 1.33\~1.41배였고, Median3도 약 1.26\~1.38배였다.

## 4. 실행시간 차이
- 병합 정렬은 비교 횟수가 가장 적었지만, **실행시간은 First·Median3 퀵 정렬보다 길었다.** 병합 정렬 / Quick(First) 시간은 1,000개에서 1.39배, 20,000개에서 1.11배였다. 20,000개에서 Median3(1.9723ms)와는 약 2% 차이(2.0107ms)로 거의 같았다.
- 비교가 적은데도 시간이 더 걸린 이유는 동작 방식에서 찾을 수 있다. 시간은 비교만이 아니라 **데이터 이동** 에도 좌우되는데, 이는 비교 횟수에 포함되지 않았다.  
  병합 정렬은 병합 때마다 모든 원소를 임시 배열에 복사하고 다시 원래 배열로 복사한다(코드의 `tmp[k++] = ...`과 `a[k] = tmp[k]`). 퀵 정렬은 제자리에서 교환만 한다.
- 크기가 커질수록 병합 정렬과 퀵 정렬의 시간 차이는 줄어드는 경향을 보였다(위 1.39배 → 1.11배). 다만 100회 모두 같은 원본 데이터로 측정한 평균이고 프로그램을 다시 실행하면 값이 달라질 수 있으므로, 이 경향을 확정하려면 데이터를 바꿔 가며 여러 번 실행해 보아야 한다.
- n이 2배가 될 때 시간은 약 2.0\~3.2배 늘었다. 비교 횟수(약 2.0\~2.4배)보다 작은 크기에서 더 크게 늘어난 경우가 있었는데, 시간이 매우 짧아 측정 오차의 비중이 커서일 수 있다.

## 5. 퀵 정렬의 피벗 선택 방법에 따른 성능 차이
### 비교 횟수
- 세 방법의 차이는 크지 않았다. Median3는 First보다 6개 크기 모두에서 적었고(1.4\~6.0% 적음), 특히 큰 크기에서 차이가 컸다(16,000개 5.2%, 20,000개 6.0%).
- Random은 First와 방향이 일정하지 않았다. 4,000·8,000·16,000개에서는 First보다 많았고(최대 6.5%), 20,000개에서는 4.8% 적었다.
- 6개 크기의 비교 횟수 합계는 Median3 815,870 < First 856,988 < Random 864,796이었다. 이번 실험에서는 **Median3가 가장 적었다.**
- 이유: 피벗이 구간을 균형 있게 나눌수록 재귀 깊이가 얕아지고, 한 번의 분할로 줄어드는 구간이 커져서 전체 비교가 줄어든다. Median3는 세 값의 가운데 값을 골라서 극단적인 값을 피벗으로 뽑을 가능성을 줄인다.
- 크기마다 데이터를 한 번만 생성해 비교 횟수를 측정했으므로 차이가 우연일 수 있다. 같은 이유로, 이번 결과에서 First와 Random의 우열은 말하기 어렵다.

### 실행시간
- **Random이 모든 크기에서 가장 느렸다.** First 대비 1.37\~2.73배였다. 비교 횟수는 First와 비슷했는데 시간만 길었으므로, 원인은 비교가 아니라 **분할마다 난수를 생성하는 비용**일 가능성이 크다. 난수 생성은 비교 횟수에 포함하지 않았기 때문에 횟수에는 나타나지 않는다.
- Median3는 1,000\~4,000개에서 가장 빨랐다(First 대비 0.82\~0.96배). 8,000개 이상에서는 First와 비슷하거나 조금 느렸다(1.02\~1.09배). 중앙값 결정에 드는 비교가 추가되는데, 비교 횟수를 줄이는 효과가 그 비용을 항상 넘지는 못한 것으로 보인다.
  다만 시간 차이가 작아서 측정 변동일 가능성도 있다.
- 종합하면, 비교 횟수는 Median3가 가장 적었고 실행시간은 First와 Median3가 비슷했다. Random은 시간이 가장 불리했다.

## 6. 메모리 사용량의 측정 방법과 계산 기준
프로파일링 도구를 쓰지 않고 **직접 계산**했다. 원본 데이터 배열은 공통 비용이므로 제외했다.

- **재귀 호출 스택**: 정렬 중 최대 재귀 깊이(구간 크기가 2 이상인 호출 기준)를 코드에서 기록(`max_depth`)하고, 호출 1회(스택 프레임)의 크기를 곱했다.
  - 퀵 정렬 프레임 = 배열 포인터(8) + int 4개(16) + 피벗 방식 enum(4) + 반환 주소(8) 
  - 병합 정렬 프레임 = 배열 포인터(8) + int 4개(16) + 반환 주소(8)
  - 64비트 환경(포인터 8바이트, int 4바이트)을 가정한 값이다.
  - 위 프레임 크기는 변수 크기를 더한 근사값이며, 실제 인자·지역변수 구성과 정확히 일치하지는 않는다.

- **병합 정렬의 임시 배열**: `n × sizeof(int)`(int 4바이트 기준)를 더했다.
- **퀵 정렬**: 임시 배열이 없으므로 재귀 호출 스택만 계산했다.
- 최종 식
  - 병합 정렬 = n × 4 + 최대 깊이 × 프레임 크기
  - 퀵 정렬 = 최대 깊이 × 프레임 크기
- **한계**: 프레임 크기는 64비트 환경(포인터 8바이트)을 가정하고 변수 크기를 더한 근사값이다. 또한 병합 과정의 merge()와 퀵 정렬의 partition()에서 사용하는 함수 호출 스택은 별도로 계산하지 않았다.
  따라서 실제 프로그램의 최대 메모리 사용량과는 차이가 있을 수 있으며, 본 실험에서는 주요 임시 배열과 재귀 호출 스택을 중심으로 알고리즘 간 상대적인 메모리 사용량을 비교하였다.


## 7. 메모리 사용량 차이
- 병합 정렬은 임시 배열 때문에 메모리가 **n에 비례해서 늘었다.** n이 2배가 되면 메모리도 거의 2배(4,320 → 8,352 → 16,384 → 32,416 → 64,448)가 되었다. 16,000→20,000개 구간만 1.25배인 것은 n 자체가 1.25배 늘었기 때문이다.
  메모리의 대부분(1,000개 93%, 20,000개 99.4%)이 임시 배열이었고, 재귀 스택은 320\~480바이트(최대 깊이 10\~15 × 32바이트)로 작았다.
- 퀵 정렬은 임시 배열이 없어서 **재귀 스택만 사용했고**, 612\~1,296바이트 수준이었다. n이 20배(1,000→20,000)가 되어도 612\~864바이트(Median3), 756\~1,296바이트(First)로 거의 늘지 않았다. 재귀 깊이만 조금 늘었기 때문이다.
- 20,000개에서 병합 정렬은 Median3의 약 93배, First의 약 62배였다.
- 퀵 정렬 세 방법 중에서는 Median3의 메모리가 가장 작았다(612\~864바이트). 최대 재귀 깊이가 상대적으로 낮았다는 뜻이며, 비교 횟수에서 균형 잡힌 분할이 유리했다는 설명과 같은 방향이다. 다만 Random과 First 사이의 차이는 크기마다 일정하지 않았다.

## 8. 시간 복잡도와 공간 복잡도

| | 병합 정렬 | 퀵 정렬 |
|---|---|---|
| 시간 복잡도(평균) | O(n log n) | O(n log n) |
| 시간 복잡도(최악) | O(n log n) | O(n²) |
| 공간 복잡도 | O(n) (임시 배열) | O(log n) 평균, O(n) 최악 |

※ 위 복잡도는 일반적으로 알려진 값이다. 이번 실험은 무작위 데이터만 사용했으므로 **퀵 정렬의 최악 O(n²)은 측정으로 확인하지 못했다.** 아래는 실험 결과와의 대응이다.
- **시간 복잡도**: n·log₂n으로 나눈 비교 횟수가 크기와 상관없이 거의 일정해서(병합 0.88\~0.91, 퀵 1.15\~1.33) 두 알고리즘 모두 n·log n 추세와 맞는다. 병합 정렬은 입력과 상관없이 항상 절반으로 나누므로 분할이 균형 잡혀 있고, 이 점이 비교 횟수가 퀵 정렬보다 적었던 이유로 설명된다.
  퀵 정렬은 피벗에 따라 분할이 달라져서 비교 횟수가 더 많고 방법에 따라 흔들렸다.
- **공간 복잡도**: 병합 정렬의 메모리가 n에 비례한 것(O(n))과, 퀵 정렬이 거의 일정하게 작은 것(O(log n) 수준)이 7절의 측정과 일치한다.

## 9. 결론
1. **비교 횟수**: 병합 정렬이 모든 크기에서 퀵 정렬보다 적었다(퀵은 1.26\~1.49배). 이번 실험에서는 병합 정렬이 항상 데이터를 절반으로 나누어 처리하기 때문에 비교 횟수가 비교적 일정하게 증가했으며, 측정한 모든 데이터 크기에서 퀵 정렬보다 적은 비교 횟수를 기록했다.
2. **실행시간**: 비교가 적은 병합 정렬이 오히려 First·Median3 퀵 정렬보다 느렸다(Quick(First) 대비 1.11\~1.43배, Median3 대비 1.02\~1.71배). 병합 시 임시 배열로의 복사 같은 데이터 이동 비용이 원인으로 추정된다. 크기가 커질수록 차이가 줄었다.
3. **메모리**: 병합 정렬은 임시 배열로 n에 비례해서 늘었고, 퀵 정렬은 재귀 스택만 써서 훨씬 작았다(20,000개에서 약 62\~93배 차이).
4. **피벗**: Median3가 비교 횟수 합계에서 가장 적었다. Random은 난수 생성 비용 때문에 시간이 가장 길었다. 크기마다 데이터를 한 번만 생성해 비교 횟수를 측정했으므로 차이가 우연일 수 있다.
5. 비교 횟수를 줄이려면 병합 정렬이, 시간과 메모리를 아끼려면 퀵 정렬(First·Median3)이 유리했다. Random 피벗 퀵 정렬은 시간이 병합 정렬보다도 길었다.

## 10. 한계
- 크기마다 데이터를 한 번만 생성했다. 여러 번 데이터를 바꿔 평균을 내면 피벗 방법 간 차이를 더 확실하게 볼 수 있다.
- 실행시간은 100회 반복 평균이지만 모두 같은 원본 데이터이며, 프로그램을 다시 실행하면 값이 달라질 수 있다.
