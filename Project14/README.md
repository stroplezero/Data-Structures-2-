# 힙 정렬, 병합 정렬, 퀵 정렬의 성능 비교

## 1. 개요

- 정렬 알고리즘: 힙 정렬(최대 힙, in-place), 병합 정렬, 퀵 정렬(피벗: First / Random / Median-of-Three)
- 데이터: 0~99,999 범위의 무작위 정수(중복 허용), n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 같은 n에서는 모든 알고리즘이 동일한 원본 배열의 복사본을 사용하고, 오름차순 정렬 결과를 매번 `is_sorted()`로 검증했다.
- 측정 항목: 숫자 비교 횟수, 실행시간(ms), 추가 메모리 사용량(Byte)

### 측정 방법

| 항목 | 방법 |
|---|---|
| 비교 횟수 | 데이터 값끼리 비교할 때마다 `cmp_count++`. 반복문의 인덱스/종료 조건 검사는 제외. 힙 정렬은 힙 구성과 복구 과정의 비교를 모두 포함하고, 퀵 정렬은 Median-of-Three의 비교를 포함. Random 피벗의 난수 생성은 비교가 아니므로 제외. |
| 실행시간 | 정렬 호출 직전부터 직후까지를 고해상도 타이머로 측정. 배열 복사, 데이터 생성, 출력 시간은 제외. 같은 정렬을 100회(`REPEAT`) 반복해 평균을 구함. |
| 메모리 | 아래 "메모리 측정 방법과 계산 기준" 참고 |

## 3. 분석

### 3.1 데이터 크기 증가에 따른 비교 횟수 변화

n이 1,000에서 20,000으로 20배 늘 때 비교 횟수는 힙 약 30.3배, 병합 약 30.0배, 퀵(First) 약 27.1배, 퀵(Random) 약 27.7배, 퀵(Median3) 약 25.4배 늘었다. 20배보다는 크고 400배(n²)보다는 훨씬 작다. 세 알고리즘 모두 n·log₂n 꼴로 증가한다는 뜻이다. 
같은 기간 n·log₂n은 약 28.7배 늘어난다.

n·log₂n 대비 비교 횟수의 비율(n = 20,000, n·log₂n ≈ 285,754)은 다음과 같다.

| 알고리즘 | 비율 | 이유 |
|---|---:|---|
| 병합 | 약 0.91 | 두 정렬된 구간을 합칠 때 한쪽이 먼저 소진되면 남은 원소는 비교 없이 복사된다. 비교 횟수가 이론 하한(n·log₂n − 약 n)에 가깝다. |
| 퀵 | 약 1.2 | 피벗 기준 분할이 정확히 반반이 아니어서 평균 약 1.39·n·log₂n에 이르는 이론값보다는 작지만, 병합보다 많다. |
| 힙 | 약 1.79 | 아래 설명 참고 |

힙 정렬의 비교 횟수는 모든 n에서 병합 정렬의 약 1.9~2.0배다(n=20,000에서 510,664 / 260,840 ≈ 1.96). 원인은 `sift_down`의 동작 방식이다. 한 단계 내려갈 때마다 "두 자식끼리 비교"와 "부모와 큰 자식 비교"를 모두 수행하므로 레벨당 비교가 2번 든다. 
또 루트와 교환해 올린 원소는 원래 맨 끝에 있던 작은 값이므로, 대부분 거의 리프까지 내려간다. 그래서 힙 정렬은 약 2·n·log₂n에 가까운 비교를 하게 된다. 이 실험의 증가율(30.3배)이 다른 알고리즘보다 약간 큰 것도 같은 이유로 보인다.

### 3.2 실행시간 차이

n=20,000에서 시간은 Quick(First) 1.83ms < Merge 2.06ms ≈ Quick(Median3) 2.08ms < Quick(Random) 2.61ms < Heap 2.87ms 순이었다. 대체로 비교 횟수와 같은 방향이지만 정확히 비례하지는 않는다.

- **퀵(First)은 비교가 병합보다 많은데도 더 빠르다.** n=20,000에서 346,132회 대 260,840회인데 시간은 1.83ms 대 2.06ms다. 퀵 정렬은 제자리에서 교환만 하고 순차적으로 배열을 훑기 때문에 캐시 효율이 좋다.
  병합 정렬은 병합마다 `tmp`에 쓰고 다시 `a`로 복사하는 데이터 이동이 추가로 든다. 즉 실행시간은 비교 횟수뿐 아니라 메모리 접근과 데이터 이동량에도 영향을 받는다.
- **힙 정렬이 가장 느리다.** 비교가 병합의 약 2배이고, 부모(i)와 자식(2i+1, 2i+2)의 인덱스 차이가 커서 배열 전체를 건너뛰며 접근하므로 캐시 적중률이 낮다. 비교가 많은 것과 접근 패턴이 나쁜 것이 겹쳐, n=16,000에서는 Quick(First)의 약 2.2배(3.53ms 대 1.59ms)였다.
- **n=16,000의 힙 정렬(3.53ms)이 n=20,000(2.87ms)보다 느린 것은 이상치다.** 비교 횟수는 n에 따라 정상적으로 증가했으므로 알고리즘 때문이 아니라 측정 환경(OS 스케줄링, 다른 프로세스, 캐시 상태)의 잡음으로 추정된다. 실행시간은 0.0x~수 ms 단위라 이런 오차가 쉽게 반영된다. 100회 평균으로 줄였지만 완전히 없애지는 못했다.
- 시간 증가율도 n·log₂n과 일치한다. n이 20배 늘 때 시간은 약 18~21배 늘었다(Heap 19.3배, Merge 18.1배, Quick(First) 21.4배). 이론 증가율(약 28.7배)보다 낮은 것은 n이 작을 때 타이머 호출 오버헤드와 고정 비용의 비중이 크고, 데이터가 캐시에 모두 들어가기 때문으로 보인다.

### 3.3 메모리 사용량 차이

n=20,000에서 Heap 44B, Quick 832~992B, Merge 80,540B였다.

- **힙 정렬(44B, 모든 n에서 동일).** 재귀 없이 반복문만 쓰고 입력 배열을 그대로 힙으로 쓴다. 필요한 것은 `root`, `child`, 교환용 임시 변수 같은 지역 변수와 함수 프레임뿐이라 n과 무관한 O(1)이다.
- **병합 정렬(약 4n + 재귀 깊이 × 36B).** 병합 시 필요한 임시 배열 `tmp`(4n바이트)가 대부분을 차지한다. n이 2배가 되면 메모리도 거의 2배가 되며(4,360 → 8,396 → 16,432 → …), n=20,000에서 80,000B가 임시 배열, 나머지 540B가 스택(깊이 15)이다. 재귀 깊이는 구간을 정확히 절반씩 나누므로 항상 ⌈log₂n⌉에 가깝다.
- **퀵 정렬(재귀 깊이 × 32B).** 임시 배열이 없고 재귀 스택만 쓴다. n=1,000에서 약 576~736B(깊이 18~23), n=20,000에서 약 832~992B(깊이 26~31)로, n이 20배 늘어도 메모리는 1.3~1.7배 늘었을 뿐이다. 이는 깊이가 log n에 비례하기 때문이다. 다만 분할이 균등하지 않아 깊이가 병합 정렬(10~15)의 약 2배다. 퀵 정렬은 병합 정렬보다 약 80~100배 적은 메모리를 쓴다.

정리하면 메모리는 Heap(O(1)) < Quick(O(log n)) < Merge(O(n)) 순이고, 이 차이는 "임시 배열이 필요한가", "재귀를 쓰는가"라는 동작 방식에서 나온다.

### 3.4 퀵 정렬의 피벗 선택 방법에 따른 차이

이번 데이터는 무작위 정수라서 세 방법의 차이가 크지 않았다.

| 항목 | 관찰 |
|---|---|
| 비교 횟수 | n=20,000에서 First 346,132 / Random 341,122 / Median3 343,259로 1.5% 이내. n=16,000에서는 Median3(266,854)이 First(299,826)보다 약 11% 적었다. 대체로 Median3가 약간 적거나 비슷했고, n=1,000에서는 오히려 First보다 많았다(13,501 대 12,756). 무작위 데이터에서는 첫 원소도 이미 무작위 값이므로 분할이 크게 치우치지 않고, Median3의 이점이 비교 3~5회 추가 비용과 비슷해 효과가 상쇄되기 때문이다. |
| 실행시간 | Random이 모든 n에서 가장 느렸다(예: n=20,000에서 2.61ms 대 First 1.83ms). 호출마다 `rand()`를 두 번 호출하고 `%` 연산을 하는 비용이 매 분할마다 쌓이기 때문이다. 비교 횟수는 비슷한데도 시간이 다른 것은 이 오버헤드 때문이다. First와 Median3은 비슷했으며 Median3이 약간 느리거나 비슷했다(분할마다 비교 3~5회와 교환이 추가됨). |
| 메모리 | 재귀 깊이에 비례. Median3이 대체로 깊이가 얕았다(n=1,000에서 18, First 23, Random 21). 중앙값에 가까운 피벗을 고르므로 분할이 더 균형 잡히기 때문이다. |

**한계:** 이 실험은 무작위 데이터만 사용했다. 이미 정렬된 배열이나 역순 배열에서는 First 피벗이 한쪽으로만 분할되어 O(n²) 시간과 O(n) 스택 깊이가 되지만, Random과 Median3은 이런 입력에도 안정적이다. 따라서 이번 결과만으로 "First로 충분하다"고 결론 내리기는 어렵고, 피벗 전략의 진짜 가치는 입력이 편향된 경우에 드러난다. 또한 각 n마다 데이터를 한 번만 생성했으므로(비교 횟수는 첫 실행 값), 위의 1~10% 수준의 차이는 데이터 한 세트의 우연일 수 있다.

### 3.5 시간 복잡도와 공간 복잡도

| 알고리즘 | 최선 | 평균 | 최악 | 공간 | 안정성 | 특징 |
|---|---|---|---|---|---|---|
| 힙 정렬 | O(n log n) | O(n log n) | O(n log n) | O(1) | 불안정 | 입력에 관계없이 시간 보장, 메모리 최소, 캐시 효율 낮음 |
| 병합 정렬 | O(n log n) | O(n log n) | O(n log n) | O(n) | 안정 | 비교 횟수 최소, 임시 배열 필요 |
| 퀵 정렬 | O(n log n) | O(n log n) | O(n²) | O(log n) (최악 O(n)) | 불안정 | 평균적으로 가장 빠름, 최악 입력에 취약(피벗 전략으로 완화) |

실험 결과는 평균 시간 복잡도가 모두 O(n log n)이라는 이론과 일치한다. 점근적으로 같은 복잡도여도 상수 계수는 달랐다. 비교 횟수(병합 < 퀵 < 힙)와 실행시간(퀵 ≤ 병합 < 힙)의 순위가 다르다는 점이 이를 보여 준다. 실제 속도는 비교 횟수 외에 메모리 접근 패턴과 데이터 이동에도 좌우된다.

### 3.6 종합

| 기준 | 가장 유리 | 이유 |
|---|---|---|
| 비교 횟수 | 병합 | 구간 합병 방식이라 불필요한 비교가 적음 |
| 실행시간 | 퀵(First/Median3) | 제자리 처리와 순차 접근으로 캐시 효율이 좋음 |
| 메모리 | 힙 | 임시 배열과 재귀가 없음 |
| 최악 입력 보장 | 힙, 병합 | 항상 O(n log n) |

## 4. 메모리 측정 방법과 계산 기준

프로파일링 도구가 아니라 **직접 계산**했다. 정렬 중에 필요한 "추가" 메모리만 센다.

- **제외:** 원본 입력 배열 `a`(모든 알고리즘의 공통 비용)
- **포함:** 보조 배열, 재귀 호출 스택(프레임 크기 × 최대 재귀 깊이), 보조 변수
- **최대 재귀 깊이:** 재귀 함수 진입 시 `cur_depth++`, 종료 시 `cur_depth--`를 하며 최댓값을 `max_depth`에 기록한다.
- **스택 프레임 크기:** 64비트 환경 기준으로 인자 + 지역변수 + 반환 주소 크기를 합산했다(포인터 8B, int 4B, enum 4B).

| 알고리즘 | 계산식 |
|---|---|
| Heap | `HEAP_AUX` = 44B(고정). `sift_down`의 인자(포인터 8 + int 2개 8), 지역변수 `child`, `t` 등(int 3개 12), 반환 주소 8, `heap_sort`의 지역변수(int 2개 8). 비재귀라 호출 깊이가 쌓이지 않는다. |
| Merge | `4n + max_depth × 36B`. 임시 배열 `tmp`(4n) + `merge_sort(a, tmp, lo, hi)` 프레임(포인터 2개 16 + int 3개 12 + 반환 주소 8 = 36B)이 깊이만큼 |
| Quick | `max_depth × 32B`. `quick_sort(a, lo, hi, type)` 프레임(포인터 8 + int 3개 12 + enum 4 + 반환 주소 8 = 32B)이 깊이만큼 |

**주의:** 이 값은 이론적 근사치다. 실제 프레임 크기는 컴파일러 최적화, 레지스터 할당, 정렬(padding) 방식에 따라 다르다. 동일 기준을 모든 알고리즘에 적용했으므로 알고리즘 간 상대 비교와 n에 따른 증가 경향은 유효하다. 또한 힙 정렬의 44B와 같이 매우 작은 값은 오차 범위에 가깝다.
