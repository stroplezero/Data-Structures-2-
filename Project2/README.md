# 배열과 연결자료형(포인터) 이진트리 구현의 비교
 이진트리를 **괄호표기법**으로 입력받아 **배열**과 **연결자료형(포인터)** 두 가지로 구현하고, 메모리 사용량과 노드 관계 조회(자식·부모·형제) 효율을 비교한 과제이다.
 기존에 구현한 배열과 연결자료형 이진트리에 메모리 사용량을 구하는 기능과 노드 관계 조회 기능을 추가하였다.

## 2. 메모리 사용량 비교
### 2.1 측정 방법
 프로그램이 만든 자료구조의 크기를 'sizeof'로 계산해 **[4] 메모리 사용량**에 출력하도록 한다. 

```
배열        = (max_idx + 1) × sizeof(char)      max_idx: 노드가 있는 가장 큰 배열 번호 (0번 칸 포함)
포인터      = 노드 수 × sizeof(Node)            64비트: 24 B = data 1 + 패딩 7 + 포인터 8×2
포인터+부모 = 노드 수 × 32 B                     parent 포인터 8 B 추가
```
- 포인터+부모: 노드에 부모 포인터를 추가한 경우 (코드의 `WITH_PARENT`를 1로 설정)
- 측정 환경: Visual Studio, x64 (포인터 8 B, 배열 원소 `char` 1 B)

### 2.5 분석

**① 배열은 높이에, 포인터는 노드 수에 좌우된다.**

노드가 24개일 때 완전 트리와 오른쪽 편향 트리를 비교하면 다음과 같다.

| 트리 (노드 24개) | 배열 | 포인터 |
|---|---:|---:|
| 완전 | 25 B | 576 B |
| 오른쪽 편향 | 16,777,216 B | 576 B |

포인터는 두 트리에서 완전히 같다.
노드마다 자식 포인터 자리가 고정으로 있고 자식이 없으면 `NULL`만 넣기 때문에, 존재하지 않는 노드를 위한 공간을 잡지 않는다. 
반면 배열은 인덱스 1번부터 사용할 경우, 노드의 번호(`2i`, `2i+1`)까지 칸을 모두 잡아야 하기 때문에 깊이 내려갈수록 번호가 두 배씩 커지는 편향 트리에서 빈 칸이 폭발적으로 늘어난다.

**② 완전·포화 트리에서는 배열이 훨씬 적게 쓴다.**

번호에 빈틈이 없어 배열의 낭비가 없고, 노드마다 포인터 2개(16 B)가 붙는 포인터 구현은 배열의 약 22~23배(360 B ÷ 16 B, 576 B ÷ 25 B)를 사용하기 때문에 배열이 포인터보다 메모리를 훨씬 적게 사용한다.

**③ 편향 트리에서는 포인터가 압도적으로 유리하다.**

- 편향 트리의 배열 크기는 왼쪽 편향이 `2^(n-1) + 1`, 오른쪽 편향이 `2^n`으로 노드 수에 지수적이다. 오른쪽 자식의 번호가 `2i+1`이라 같은 노드 수에서 왼쪽 편향의 약 2배이다(24개: 8,388,609 B와 16,777,216 B).
- 노드가 10개일 때 이미 배열(513 B)이 포인터(240 B)보다 2배 이상 크고, 노드가 늘수록 격차는 45배(15개), 1,092배(20개), 14,563배(24개), 29,127배(오른쪽 24개)로 커진다.

**④ 일반 트리는 노드 수에 비해 높이가 얼마나 낮은지에 따라 유불리가 갈린다.**

- 촘촘 트리는 노드 6개가 높이 3에 모여 있어 배열이 8 B, 포인터가 144 B로 배열이 유리하다.
- 지그재그 트리는 노드가 10개뿐인데 높이가 10까지 길게 뻗어 있어 배열이 683 B, 포인터가 240 B로 포인터가 유리하다.

배열은 높이가 커질수록 필요한 칸이 크게 늘고, 포인터는 노드 수만 늘어야 커지기 때문이다.   
즉 노드 수가 같아도 높이가 낮고 촘촘하면 배열이, 높이가 높고 성기면 포인터가 유리하다.

## 3. 자식·부모·형제 조회 비교

### 3.1 측정 방법

각 구현에 자식·부모·형제를 조회하는 기능을 추가하고, 어떤 구현이 더 효율적인지 알아보기 위하여 **메모리에 접근한 횟수**를 세어 비교하였다.

| 항목 | 배열 | 포인터 |
|---|---|---|
| 노드 찾기 | 확인한 배열 칸 수 (빈 칸 포함) | 방문한 노드 수 |
| 부모 찾기 | 0 (`i/2` 계산만 하면 됨) | 부모 포인터 없음: 루트부터 재탐색한 노드 수<br>부모 포인터 있음: 0 |
| 읽기 | 자식·부모·형제 칸을 읽은 횟수 | 자식·부모·형제 노드의 값을 읽은 횟수 |

- 배열은 빈 칸을 읽어도 1회로 세고, 포인터는 `NULL`이면 노드에 접근하지 않으므로 0회로 센다.
- 각 트리에서 **가장 깊은 노드**(또는 마지막으로 찾게 되는 노드)를 조회해 비용이 큰 경우를 비교하였다.
- 포인터의 "부모 찾기"는 노드 포인터만 들고 있을 때 부모를 구하는 비용이다. 문자로 검색하면서 부모를 함께 기록해 내려가면 추가 비용 없이 구할 수 있다.

### 3.2 결과

각 칸은 `노드 찾기 / 부모 찾기 / 읽기 = 합계` 순서이다.

| 트리 | 조회 노드 | 배열 | 포인터 | 포인터+부모 |
|---|:---:|---|---|---|
| 일반 (촘촘) | G | 7 / 0 / 4 = 11 | 6 / 5 / 1 = 12 | 6 / 0 / 1 = **7** |
| 일반 (지그재그) | J | 682 / 0 / 4 = 686 | 10 / 9 / 1 = 20 | 10 / 0 / 1 = **11** |
| 완전 (포화 15개) | O | 15 / 0 / 4 = 19 | 15 / 13 / 2 = 30 | 15 / 0 / 2 = **17** |
| 완전 (24개) | X | 24 / 0 / 4 = 28 | 20 / 19 / 1 = 40 | 20 / 0 / 1 = **21** |
| 편향 (왼쪽 10개) | J | 512 / 0 / 4 = 516 | 10 / 9 / 1 = 20 | 10 / 0 / 1 = **11** |
| 편향 (왼쪽 15개) | O | 16,384 / 0 / 4 = 16,388 | 15 / 14 / 1 = 30 | 15 / 0 / 1 = **16** |
| 편향 (왼쪽 20개) | T | 524,288 / 0 / 4 = 524,292 | 20 / 19 / 1 = 40 | 20 / 0 / 1 = **21** |
| 편향 (왼쪽 24개) | X | 8,388,608 / 0 / 4 = 8,388,612 | 24 / 23 / 1 = 48 | 24 / 0 / 1 = **25** |
| 편향 (오른쪽 24개) | X | 16,777,215 / 0 / 4 = 16,777,219 | 24 / 23 / 1 = 48 | 24 / 0 / 1 = **25** |

### 3.3 분석

(n: 노드 수,  h: 트리의 높이)
| 연산 | 배열 | 포인터 (부모 포인터 없음) | 포인터 (부모 포인터 있음) |
|---|---|---|---|
| 노드 찾기 | O(배열 크기) = O(2^h)* | O(n) | O(n) |
| 자식 | O(1) | O(1) | O(1) |
| 부모 | O(1) | O(n) | O(1) |
| 형제 | O(1) | O(n) | O(1) |

※배열 전체 메모리 공간(최대 인덱스)을 스캔해야 해서 $O(\text{Max Index}) = O(2^h)$ 수준으로 비효율적이다.

**① 자식 조회는 두 구현이 같다.** 배열은 `2i`, `2i+1`, 포인터는 `left`, `right`로 모두 한 번에 구한다.

**② 부모·형제는 배열이 즉시 구하고, 포인터는 부모 포인터가 있어야 한번에 구할 수 있다.** 
 배열은 번호 계산만으로 부모와 형제를 얻지만, 부모 포인터가 없는 포인터 구현은 루트부터 다시 탐색해야 해서 조회 노드가 깊을수록 비용이 커진다(완전 15개의 `O`는 13회, 편향 24개의 `X`는 23회).

**③ 완전 트리에서는 배열이 부모 포인터 없는 포인터보다 효율적이다.** 
 완전 트리에서의 합계에서 배열 대 포인터가 19 대 30, 28 대 40으로 배열이 적은데, 배열 크기가 노드 수와 거의 같아 탐색 낭비가 없고, 부모·형제가 계산으로 끝나기 때문이다. 
 포인터에 부모 포인터를 달면 합계가 17, 21로 배열과 비슷하거나 약간 적은 수준이 된다.

**④ 편향·희소 트리에서는 배열의 노드 찾기가 크게 비싸다.** 
 배열은 빈 칸까지 모두 훑어야 해서 탐색 비용이 노드 수가 아닌 배열 크기에 비례한다. 오른쪽 편향 24개의 마지막 노드를 찾는 데 16,777,215칸을 확인했지만, 포인터는 24개 노드만 방문하면 된다.

 **⑤ 정리.** 
 완전 트리에서는 배열이 부모 포인터 없는 포인터보다 적은 접근으로 끝나 더 효율적이다(19 대 30, 28 대 40).   
 편향·희소 트리에서는 노드 찾기 비용이 배열 크기에 비례해 폭증하므로 포인터가 더 효율적이다(편향 24개: 16,777,219 대 48).   
 포인터에 부모 포인터를 추가하면 표의 모든 트리에서 접근 횟수가 가장 적지만, 노드당 8 B(약 33%)의 메모리가 더 든다.

|---|---|---|
| 완전·포화 트리 | **배열** | 메모리가 포인터의 약 1/22 수준 (15개: 16 B 대 360 B, 24개: 25 B 대 576 B), 부모·형제를 계산으로 즉시 구함 |
| 편향 트리 | **포인터** | 24개에서 배열 최대 16,777,216 B 대 포인터 576 B, 노드 찾기도 16,777,215칸 대 24노드 |
| 일반 트리 | 높이에 따라 다름 | 노드 수에 비해 높이가 낮으면 배열, 높이가 크게 늘면 포인터 (촘촘 8 B 대 144 B, 지그재그 683 B 대 240 B) |

- 배열 구현의 효율은 **트리가 얼마나 빈틈없이 채워졌는지**에 달려 있다. 완전 트리라면 메모리와 조회 속도 모두에서 가장 효율적이지만, 편향·희소 트리에서는 메모리와 탐색 비용이 노드 수의 지수 배로 늘어난다.
- 포인터 구현은 노드마다 고정 비용(포인터 2개)이 들지만 **모양과 무관**하게 노드 수에 비례하므로 어떤 트리에서도 안정적이다. 부모·형제 조회는 부모 포인터를 추가해 보완할 수 있다.
- 따라서 "어느 구현이 더 효율적인가"는 트리의 모양에 따라 달라지며, 완전·포화 이진트리에는 배열을, 편향 트리에는 포인터를 선택하는 것이 합리적이라 할 수 있다.
